\paragraph{¿Cuál es la diferencia entre un cable de UTP directo y uno cruzado?}

  Para cables UTP existen 2 estándares, \code{T568A} y \code{T568B} como se muestra en la figura \ref{fig:utp}.

    \begin{figure}[h!]
      \center
      \input{sections/utp-directo-cruzado.tex}
      \caption{Diagrama que muestra la conexión de un cable UTP cruzado vs directo.}
      \label{fig:utp}
    \end{figure}

    Estos estándares dictan dónde se posicionan los pines de transmitir y recibir (\code{Tx} y \code{Rx}).
    Cuando se habla de un cable UTP directo, se refiere a un cable en el que ambos lados son del mismo estándar, 
    mientras que un cable cruzado tiene estándares diferentes.

    Esto significa que un cable UTP directo, sin importar si es \code{T568A} o \code{T568B}, no cambia la 
    organización de los cables.
    Por el contrario, un cable UTP cruzado va a cambiar la organización de los cables.

    Se hace así porque los puertos de los dispositivos de red (como routers o switches) tienen una 
    organización diferente a los puertos de los dispositivos finales (como computadores).
    De modo que una conexión entre un switch y un computador requiere solo un cable directo porque los puertos 
    están físicamente organizados para que \code{Tx} vaya a \code{Rx} y viceversa.
    Pero en las ocasiones en que se requiere conectar 2 dispositivos de red, lo que causa que los puertos se vayan 
    en la dirección incorrecta, por esto se requiere un cable UTP cruzado.

    Aunque dispositivos \textit{modernos} pueden detectar la configuración incorrecta y corregirla internamente, 
    como es el caso del switch \code{C2960}, de acuerdo con el fabricante \cite{cisco_2960_auto_mdix}.
    Por tanto, es irrelevante que el switch utilizado use un cable cruzado en este laboratorio.

\paragraph{¿Por qué se realiza toda esta configuración básica a los dispositivos 
    switch y router?}

Dado que los dispositivos que vienen con configuración de fábrica no tienen ninguna contraseña, son vulnerables a
ataques bastante simples. Las configuraciones, específicamente las contraseñas, permiten agregar una capa de seguridad
contra actores maliciosos. También se configuró el nombre del dispositivo en terminal para que sea más fácil
diferenciarlo; esto es especialmente útil si no se está físicamente cerca del dispositivo. Además, se activó el acceso a
terminal de manera remota, con su respectiva contraseña.

\paragraph{¿Por qué la configuración del direccionamiento IP es distinta entre un PC, 
un switch, un router y un hub?}

Para empezar, un hub es un dispositivo \textit{estúpido}, solo envía todo lo que recibe a todo lo 
que está conectado; no es configurable remotamente porque no es configurable en sí, prácticamente es un cable 
más complejo. Por tanto, no se le asigna ni configura una IP.

Por el contrario, un router maneja el enrutamiento y por tanto requiere una IP y una subred para saber 
\textit{dónde está} en el árbol de todas las posibles IP. Además, puesto que el enrutamiento puede incluir 
múltiples subredes, el router requiere saber con qué IP se presenta en cada puerto.

Mientras que un switch no maneja enrutamiento y no es un dispositivo activo en ninguna conexión 
excepto como medio por el cual se realiza la conexión. Esto sin incluir configuraciones administrativas 
remotas, que es una de las únicas razones por las que se le asigna una IP a un switch.

\paragraph{¿Por qué se asigna el direccionamiento del switch en la interfaz VLAN 1, 
mientras que al router se le asigna en otra interfaz?} Porque el direccionamiento IP de un switch es para configurarlo
remotamente, mientras que el direccionamiento IP de un router es para que el router pueda \textit{enrutar} acorde a la
subred de la que está recibiendo y enviando los paquetes. Un router está hecho para enrutar y necesita un puerto
por cada subred que está manejando. Un switch no; un switch solo requiere una IP para administración.

\item Pruebas de conectividad End-to-End (E2E)

  Una vez realizadas las conexiones y configuraciones anteriores, se ejecutaron las pruebas de 
  conectividad usando el comando \code{ping}.

  \paragraph{PC-A — SW-A}
  \begin{itemize}
    \item \textbf{¿Se pudo realizar la prueba?} Sí, aunque este tal vez no sea el resultado esperado si se considera el
      uso de un cable UTP cruzado. Sin embargo, como se mencionó anteriormente, el switch utilizado en la práctica usa
      auto MDI/MDIX, por lo que no importa si se usa cable directo o cruzado.
    \item \textbf{¿Cómo se realizó la prueba?} Se utilizó la terminal de Windows (\textit{CMD}) con el comando \code{ping}.
    \item \textbf{¿La prueba fue exitosa?} Sí.
  \end{itemize}

  \paragraph{PC-A — Router}
  \begin{itemize}
    \item \textbf{¿Se pudo realizar la prueba?} Sí, pero la primera prueba falló.
    \item \textbf{¿Qué ocurrió?} Inicialmente se recibió el mensaje “Host de destino inaccesible”.
    \item \textbf{Solución:} Se corrigió la conexión física entre el router y el switch.
    \item \textbf{Resultado final:} La prueba fue exitosa.
  \end{itemize}

  \paragraph{Router — SW-A}
  \begin{itemize}
    \item \textbf{¿Se pudo realizar la prueba?} Sí.
    \item \textbf{Resultado:} Conectividad exitosa sin problemas.
  \end{itemize}

\paragraph{¿Cuál es el propósito de estas pruebas?}

Permiten verificar el correcto funcionamiento de la red y diagnosticar errores. Son comparables al uso de un multímetro
en circuitos eléctricos, ya que ayudan a identificar fallas y validar el sistema.
